01

Fundamentals

The core mental model before anything else.
Q1. Explain the React Native Animated API and how an animation progresses from start to finish.

Animated is a declarative system built around Animated.Value — a mutable number container that React components subscribe to without re-rendering on every tick.

The lifecycle: you create a value, wire it into a style via interpolate or directly, call an animation function (timing/spring/decay), and call .start(). Internally it schedules updates every frame (via requestAnimationFrame on JS, or entirely on the UI thread when native-driven), pushing new values to the connected view until the end condition is met, then invokes the completion callback with { finished: true }.

Q2. Difference between Animated.timing, spring, and decay?
  • timing — moves from A to B over a fixed duration using an easing curve. Predictable, deterministic.
  • spring — physics-based, driven by tension/friction (or stiffness/damping). No fixed duration; it settles naturally, ideal for gesture-driven UI that should feel alive.
  • decay — starts with a velocity and gradually slows via a deceleration factor until it stops. Used for momentum/fling effects, e.g. after a swipe release.
Q3. What is Animated.Value vs Animated.ValueXY?

Animated.Value holds a single scalar (opacity, single-axis translate). Animated.ValueXY is a convenience wrapper holding two Animated.Values (x and y) as one object — useful for 2D drag/pan gestures so you don't juggle two separate values, and it exposes helpers like getLayout() and getTranslateTransform().

Q4. What does useNativeDriver: true actually do?

It serializes the animation configuration (start/end values, easing, duration) once and hands it off to the native side (via the old bridge or the new JSI-backed runtime). From that point, every frame is computed and applied directly on the UI thread using native animation APIs (Core Animation on iOS, the animation framework on Android) — completely bypassing the JS thread per-frame. That's why it stays smooth even if JS is busy or blocked.

Q5. Which properties can and cannot be animated using the native driver?

Can: transform properties — translateX/Y, scale, scaleX/Y, rotate — plus opacity. These don't affect layout, so the native side can apply them without touching Yoga/layout.

Cannot: layout properties — width, height, top, left, margin, flex — because changing them requires re-running layout, which only the JS/Shadow thread can trigger. Animating these forces you off the native driver, or requires a transform-based workaround.

Q6. What is interpolation? Give a real-world example.

Interpolation maps an input range to an output range — letting one driving value control multiple visual properties, including non-numeric ones like colors or rotation strings.

const rotate = scrollY.interpolate({
  inputRange: [0, 100],
  outputRange: ['0deg', '180deg'],
  extrapolate: 'clamp',
});

Real example: a pull-to-refresh spinner where scroll offset 0→100 drives icon rotation 0deg→180deg, and simultaneously opacity 0→1 — one value, multiple derived outputs.

Q7. How would you create a fade-in + slide-up animation?
const opacity = useRef(new Animated.Value(0)).current;
const translateY = useRef(new Animated.Value(20)).current;

useEffect(() => {
  Animated.parallel([
    Animated.timing(opacity, { toValue: 1, duration: 300, useNativeDriver: true }),
    Animated.timing(translateY, { toValue: 0, duration: 300, useNativeDriver: true }),
  ]).start();
}, []);

// style: { opacity, transform: [{ translateY }] }

Both properties are transform/opacity, so both stay eligible for the native driver, running in true parallel on the UI thread.

Q8. How do you sequence or run multiple animations in parallel?
  • Animated.sequence([a, b, c]) — runs one after another.
  • Animated.parallel([a, b]) — runs simultaneously.
  • Animated.stagger(100, [a, b, c]) — parallel, but each starts with a delay offset — good for list-item entrance effects.

All three are composable — you can nest a parallel inside a sequence step.

02

Performance — Senior Level

Where interviews start probing for real production experience.
Q9. Your animation drops frames whenever an API response is processed. How would you debug and fix it?

Debug: open Flipper/Perf Monitor, watch the JS FPS graph vs UI FPS graph during the response handling — if only JS FPS dips, the culprit is synchronous work on that thread (JSON parsing, large state updates, re-renders), not the animation itself.

Fix: confirm the animation is running with useNativeDriver: true so it's immune to the JS stall; move heavy parsing/transformation off the critical path (chunk it, defer with InteractionManager.runAfterInteractions, or offload to a worker); avoid triggering large re-renders synchronously with the response — batch or debounce state updates.

Q10. Explain the relationship between the JS thread, UI thread, and animation performance.
JS Thread — runs your React logic, event handlers, state, network calls
↕ bridge / JSI
Shadow Thread — computes layout via Yoga
↕
UI Thread — actually draws each frame, must hit 60/120fps

Animations look janky whenever the thread responsible for producing the next frame is blocked. Native-driven animations run entirely on the UI thread, so they survive a busy JS thread. Non-native-driven animations depend on the JS thread computing and sending each frame's value across the bridge — any JS-side blocking work directly causes dropped frames.

Q11. Why can an animation still lag even when useNativeDriver: true?
  • The UI thread itself is overloaded — too many simultaneous native animations, heavy view hierarchies, or expensive shadow/layout work competing for the same thread.
  • The animated property triggers layout recalculation indirectly (e.g. an Image resizing).
  • Bridging overhead at animation start — the initial config serialization and any listener callbacks (.addListener) still cross to JS every frame, which reintroduces bridge cost.
  • Large images decoding, heavy shadows/blur, or high view count causing GPU-side (not thread-side) rendering bottlenecks.
Q12. How would you identify whether jank is caused by JS, UI rendering, or excessive layout work?
  • Perf Monitor / Flipper — two separate FPS graphs for JS and UI; a drop in only one narrows the cause immediately.
  • Systrace / Android Studio Profiler — shows time spent in layout passes vs draw calls vs JS execution.
  • Hermes sampling profiler — flags expensive JS functions running during the animation window.
  • Manually toggle useNativeDriver or temporarily strip layout-affecting props to isolate the variable.
Q13. What happens if you update React state on every animation frame?

Every state update triggers a re-render, reconciliation, and (potentially) a new layout pass — all on the JS/Shadow thread, at up to 60 times a second. This is precisely what Animated/Reanimated are designed to avoid: they mutate values imperatively and push them straight to the native view, never touching React's render cycle. Doing this manually with setState reliably tanks FPS and is a common junior-level anti-pattern.

Q14. How would you optimize animations in a list containing 500+ items?
  • Use FlatList/FlashList with windowSize, maxToRenderPerBatch, and getItemLayout tuned so off-screen items never enter the render/animation pipeline.
  • Animate with the native driver so per-item transforms don't hit JS.
  • Memoize row components (React.memo) so an animation on one row doesn't re-render siblings.
  • For entrance effects use Animated.stagger only on visible items, not the whole dataset.
  • Prefer Reanimated for list item animations since shared values live off the JS thread entirely, sidestepping re-render cost altogether.
Q15. How can excessive re-renders affect animations?

Every re-render forces reconciliation of the component subtree, which competes for the same JS thread that non-native-driven animations depend on to compute frames — and can even interrupt native-driven animations if it triggers layout thrash. Practically: an animating component wrapped in a parent that re-renders on every keystroke or every socket message will visibly stutter, even though the animation "shouldn't" care about React state at all.

03

Reanimated

The library senior candidates are expected to know deeply, not just recognize.
Q16. Why would you choose Reanimated over the React Native Animated API?

Reanimated runs animation and gesture-response logic entirely on the UI thread via worklets — not just the final interpolated frame like useNativeDriver does. That means you can write conditional, stateful animation logic (not just start/end value transitions) that never round-trips to JS. It also supports animating layout-affecting properties (via the Layout Animations API), which the classic native driver can't do, and gives synchronous, jank-free response to gestures.

Q17. Explain Shared Values in Reanimated.

A shared value (created with useSharedValue) is a mutable container accessible from both the JS and UI thread simultaneously, backed by the same underlying memory via JSI. Reading/writing .value doesn't trigger a React re-render — it's the Reanimated equivalent of Animated.Value, but with direct, synchronous cross-thread access instead of a serialized bridge hop.

Q18. What is a worklet?

A worklet is a small JavaScript function marked (implicitly by Babel plugin, or explicitly with 'worklet') so Reanimated can extract, serialize, and run it directly on the UI thread's own JS runtime — independent of the main JS thread. It's the mechanism that lets your animation/gesture logic execute without crossing the bridge on every frame.

Q19. Where does a Reanimated worklet execute?

On a separate, secondary JavaScript runtime that lives on the UI thread — not the main JS thread, and not literally "native code." Reanimated spins up this UI-thread JS runtime via JSI so worklets can run alongside frame rendering with no bridge serialization cost.

Q20. Difference between useSharedValue, useDerivedValue, and useAnimatedStyle.
  • useSharedValue — creates the raw mutable value itself.
  • useDerivedValue — creates a read-only value computed from one or more shared values, automatically recalculated (on the UI thread) whenever a dependency changes. Used for derived state, not for styling directly.
  • useAnimatedStyle — a worklet that returns a style object built from shared/derived values; Reanimated applies it directly to the native view every frame, bypassing React's render cycle entirely.
Q21. What is the purpose of runOnJS?

Worklets run on the UI thread and can't directly call regular JS-thread functions (e.g. setState, navigation, analytics, network calls). runOnJS(fn)(args) schedules that function to run back on the main JS thread — it's the deliberate, explicit bridge back across threads.

Q22. Why should runOnJS be used carefully?

Every call re-introduces cross-thread communication — the exact cost Reanimated exists to avoid. Calling it every frame (e.g. inside onActive of a pan gesture to update React state continuously) reproduces the same jank you'd get from setState-per-frame in classic Animated. Best practice: keep the hot path (every-frame updates) purely in shared values/worklets, and only runOnJS at discrete moments — gesture end, threshold crossed, animation finished.

Q23. Difference between withTiming, withSpring, and withDecay.

Direct worklet-thread equivalents of the classic API: withTiming = duration + easing curve, withSpring = physics-based settle (damping/stiffness), withDecay = velocity-driven deceleration. The key difference from Animated is these run and can be composed/chained (withSequence, withRepeat) entirely on the UI thread as plain worklet function calls, with no bridge hop per frame.

Q24. How does Reanimated avoid frequent JS ↔ native communication?

Three mechanisms working together: (1) shared values live in memory accessible from both runtimes via JSI, no serialization needed to read/write; (2) worklets execute the actual animation/gesture math on the UI-thread runtime, so decisions happen where the frame is drawn; (3) useAnimatedStyle writes directly to the native view's props each frame without going through React's reconciler. The main JS thread is only touched when you explicitly opt in via runOnJS.

Q25. What happens when you access a normal JS variable inside a worklet?

Worklets capture variables from the enclosing JS-thread closure by value at the time the worklet is created (Babel serializes the closure). So reading a plain variable gives you a snapshot, not a live reference — and writing to it inside the worklet does not propagate back to the JS thread. This is exactly why shared values exist: they're the one type of "variable" that's genuinely synchronized across both runtimes.

Gotcha

Mutating a captured plain object/array inside a worklet silently does nothing useful on the JS side — a classic interview trap question.

04

Gesture + Animation

Where Reanimated and react-native-gesture-handler meet.
Q26. How would you implement a swipe-to-delete interaction?

Wrap the row in a Gesture.Pan(), drive a shared value translateX directly from event.translationX in onUpdate. On onEnd, check translation against a threshold (and/or velocity): past it, animate off-screen with withTiming and call an onDelete callback via runOnJS once finished; under it, spring back to zero with withSpring. Pair with useAnimatedStyle for the transform and often an interpolated background color/icon opacity for delete-affordance feedback.

Q27. How would you build a draggable bottom sheet?

A shared value translateY tracks sheet position, clamped between an open and closed offset. A pan gesture updates it directly on drag; onEnd compares final position + velocity against snap points and animates to the nearest one with withSpring. Backdrop opacity is a useDerivedValue interpolation of the same translateY, so it's perfectly in sync with zero extra state. For production, reaching for @gorhom/bottom-sheet (built on Reanimated + Gesture Handler) is usually the pragmatic answer over a from-scratch build.

Q28. How would you implement a Tinder-style swipe card?

Track translateX/translateY shared values from a pan gesture; derive a rotation (useDerivedValue, interpolating translateX to a few degrees) so the card tilts as it moves — the signature feel. On release, compare horizontal distance/velocity to a threshold: past it, withTiming the card off-screen in that direction and trigger the next-card logic via runOnJS; otherwise withSpring back to center. Stack the next card underneath with a subtle scale/opacity interpolation driven by the top card's progress for a layered feel.

Q29. How do Gesture Handler and Reanimated work together?

Gesture Handler recognizes native touch gestures on the UI thread and exposes their event stream. When gesture callbacks are written as worklets (the modern Gesture.Pan().onUpdate(event => {'worklet'}) API), the entire gesture-to-animation pipeline — recognition, value update, style application — stays on the UI thread with zero bridge hops, which is what makes drag interactions feel perfectly attached to the finger.

Q30. How would you prevent a gesture from conflicting with a ScrollView?
  • Use Gesture Handler's composition APIs — Gesture.Simultaneous, Gesture.Exclusive, or Gesture.Race — to explicitly define which gesture wins in overlapping regions.
  • Constrain the custom gesture's activation area with activeOffsetX/failOffsetY so, e.g., a horizontal swipe only activates once horizontal movement clearly exceeds vertical, letting vertical drags fall through to the ScrollView.
  • Use simultaneousHandlers/waitFor refs to sequence recognition against the ScrollView's own pan responder.
Q31. How would you implement a swipe threshold?
const SWIPE_THRESHOLD = SCREEN_WIDTH * 0.3;

.onEnd((event) => {
  const shouldDismiss =
    Math.abs(translateX.value) > SWIPE_THRESHOLD ||
    Math.abs(event.velocityX) > 800;

  if (shouldDismiss) {
    translateX.value = withTiming(Math.sign(translateX.value) * SCREEN_WIDTH);
  } else {
    translateX.value = withSpring(0);
  }
});

Good thresholds combine distance and velocity — a fast short flick should dismiss just as reliably as a slow long drag.

05

Real-World Scenarios

Scenario-style questions that test applied judgment, not recall.
Q32. Video scrubber becomes jittery while dragging. How would you design it?

Jitter here usually means the scrub position is round-tripping through React state (or the JS thread) on every pixel of movement. The fix is to keep the whole interaction on the UI thread:

Gesture (Pan)
↓
Shared Value (scrub position)
↓
UI-thread animation (useAnimatedStyle)
↓
Animated thumb position
↓
JS only when necessary (seek call, throttled)

The player's actual seek() call is expensive and shouldn't fire every frame — throttle it, or only call it via runOnJS on release (or at a coarse interval during drag), while the visual thumb tracks the finger at full frame rate purely through the shared value.

Q33. Bottom sheet that follows the finger and snaps open/closed on release based on velocity + position. How would you implement it?

Same pan-gesture-drives-shared-value pattern as Q27/Q31, but the snap decision blends two signals rather than one:

.onEnd((event) => {
  const pastMidpoint = translateY.value > SHEET_HEIGHT / 2;
  const flickingDown = event.velocityY > 500;
  const flickingUp = event.velocityY < -500;

  const shouldClose = flickingDown || (pastMidpoint && !flickingUp);
  translateY.value = withSpring(shouldClose ? CLOSED_Y : OPEN_Y, { velocity: event.velocityY });
});

Passing the release velocity into withSpring is what makes the settle feel physically continuous with the drag, instead of visibly "restarting."

Q34. An animation running during navigation occasionally freezes. What would you investigate?
  • Whether the animation is native-driven — non-native-driven animations are especially vulnerable to freezing during a navigation transition, which is itself JS-thread-heavy work (screen mount, context providers, effects firing).
  • Whether the navigator is unmounting/remounting the animating component mid-flight, killing the Animated.Value or shared value entirely rather than pausing it.
  • Whether InteractionManager interactions are queued and blocking, or the navigation library's own transition animation is competing for the same UI thread resources.
  • Whether heavy work (data fetching, large list rendering) is kicked off synchronously on the destination screen's mount, stalling JS right as the transition needs it.
Q35. Animate height from 0 → 300 with useNativeDriver: true. What problem will you face, and what alternatives?

Problem: height is a layout property — it isn't supported by the native driver at all, and attempting it throws/falls back silently depending on RN version, losing the native-driver benefit.

Alternatives:

  • Animate a scaleY transform on a fixed-height container instead (works with native driver, but clips/scales content rather than reflowing it — fine for solid blocks, wrong for text).
  • Use the RN LayoutAnimation API for the whole transition instead of manually animating one property.
  • Use Reanimated's Layout Animations (Layout, entering/exiting transitions, or an animated useAnimatedStyle for height run on the UI thread) — Reanimated can animate layout properties smoothly because it computes the frame on the UI thread directly, unlike the classic native driver.
  • Fall back to non-native-driven Animated.timing for just the height value if precise, reflowing height animation is required and Reanimated isn't available.
06

Architecture / Lead-Level

System-level thinking for staff/lead-track interviews.
Q36. When would you choose Animated API, LayoutAnimation, Reanimated, or CSS/web-style animation?
  • Animated API — simple, isolated transform/opacity animations with no gesture involvement; low complexity, no extra dependency, sufficient for most one-off UI polish.
  • LayoutAnimation — one-shot layout transitions (item add/remove/reorder) where you want RN to auto-animate the before/after layout diff without writing explicit interpolations.
  • Reanimated — anything gesture-driven, anything needing complex per-frame logic, anything performance-critical at scale, or animating layout properties smoothly. The default choice for serious production apps today.
  • CSS/web-style (relevant mainly for React Native Web or Expo web targets) — when the same codebase renders to web and you want to lean on native browser compositing for that target specifically.
Q37. How would you design a reusable animation system for a large React Native application?
  • A shared motion token layer — standardized durations, easing curves, and spring configs (e.g. motion.duration.fast, motion.spring.snappy) so every screen feels consistent instead of each engineer picking arbitrary numbers.
  • A small library of reusable animated primitives (FadeInView, PressableScale, Collapsible, Sheet) built once on Reanimated, exposed with simple declarative props.
  • Shared custom hooks encapsulating common patterns (useFadeIn(), useSwipeToDismiss()) so gesture + shared-value wiring isn't duplicated per feature team.
  • Documented guidelines on when to reach for which tool (tying back to Q36), enforced lightly via code review/lint rather than rigid restriction.
Q38. How would you prevent every screen from creating its own animation logic?

Treat it as an API design problem: publish an internal @app/motion package exposing the primitives and hooks from Q37 with a small, opinionated surface area — so the path of least resistance for a feature engineer is to compose existing pieces, not hand-roll a new useSharedValue setup. Pair that with lightweight lint rules or PR-template prompts flagging raw Reanimated/Animated usage outside the shared package, and periodic audits to fold recurring one-off patterns back into the library.

Q39. How would you handle animations in a media-heavy application?
  • Keep all animation logic on the UI thread (Reanimated/native driver) since the JS thread is already contended by media decoding, buffering callbacks, and playback state.
  • Avoid animating during heavy media transitions (e.g. video codec swaps) where possible, or reduce animation complexity during those windows.
  • Lazy-load and downsample thumbnails/previews used in animated lists so decode cost doesn't stack with animation cost.
  • Profile GPU load specifically, not just thread load — video rendering, blur effects, and transform animations all compete for the same GPU budget, which thread-level profiling won't show directly.
Q40. 10 simultaneous animations, video playback, network requests, a large FlatList — FPS drops. Walk through your debugging and optimization strategy.

1. Isolate the layer. Use Perf Monitor/Flipper to see JS FPS vs UI FPS separately — determines whether the bottleneck is thread contention, GPU/draw cost, or both.

2. Audit the animations. Confirm every one of the 10 is native-driven or Reanimated-worklet-based; any non-native-driven animation running concurrently with network/list work is a prime suspect.

3. Audit the list. Check FlatList tuning (windowSize, getItemLayout, memoized rows) — an unoptimized large list is often the single biggest FPS cost, independent of the animations.

4. Audit network handling. Ensure response parsing/state updates aren't synchronous and large; batch state updates, defer non-critical work with InteractionManager.

5. Audit media. Confirm video decoding isn't competing for the same GPU budget as multiple simultaneous transform/opacity animations; consider reducing concurrent animation count or complexity while video is actively playing.

6. Reduce, don't just optimize. Ask whether all 10 animations genuinely need to run simultaneously — staggering, deferring off-screen ones, or simplifying to opacity-only for less critical elements is often the highest-leverage fix.

Signal

This question is really testing whether the candidate reaches for holistic system profiling first, rather than guessing and micro-optimizing one animation in isolation.
